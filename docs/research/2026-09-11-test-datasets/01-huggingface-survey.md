# Survey: existing (Python function, unit test) datasets for pytest SFT curation

Target: ≥5,000 usable (pure function, pytest module importing `from solution import <name>`, test passes and kills ≥1 mutant) pairs after our own filtering. This report finds raw material only — no filtering performed here beyond ruling out datasets that are structurally wrong (Java, I/O judges, no tests at all).

**Cutoff caveat applies to all rows below**: our held-out pool is GitHub code created after 2026-06-01. Every dataset found — HF-hosted or not — has a source/generation cutoff no later than mid-2025, so **none of these can leak the held-out pool**. That's a non-issue for contamination; it does mean none of them are "fresh" and all need de-duplication against whatever benchmark we eval on.

## Notes on verification confidence

Everything above came from the HF dataset card text as rendered by an automated fetch, not from downloading and inspecting actual rows. Treat "format" and "test style" columns as **card claims, not confirmed by execution** — before committing engineering time to any of these, pull 20-50 rows and check by hand that (a) the function is genuinely pure (no I/O/network), (b) the test file, as given, actually imports the function the way we need (`from solution import <name>`) or can be mechanically rewritten to do so, and (c) the pass rate against the given solution is close to 100% (synthetic datasets sometimes ship with tests that don't actually pass the paired solution).

Datasets I could not open (UniTSyn artifact, CAT-LM artifact, SWE-smith standalone card) are marked "unverified" — a GitHub/arXiv search pass (blocked this session by the web-search quota) would likely resolve those; recommend a follow-up session with WebSearch available specifically for UniTSyn and CAT-LM, since UniTSyn's stated method (LSP-based focal/test pairing straight from GitHub) is the best structural match to our task if the artifact actually exists.

Also ruled out immediately, no card-level ambiguity: **methods2test is Java** (JUnit), not Python — despite being the most obvious "focal method + test" precedent by name, it's the wrong language entirely and only useful as a methodology reference (how they extracted focal-method/test pairs) for building our own extraction pipeline against Python repos. **jinaai/code_exercises** and **Vezora/Tested-143k-Python-Alpaca** both looked promising by size but have **no test field at all** — ruled out on inspection, a reminder that "tested"/"exercises" in a dataset name doesn't guarantee unit tests exist.

## Top 5 ranked for our purpose

**1. KodCode-V1** is the strongest volume play. 484k synthetic rows, explicitly generated as pytest-style function+test pairs by GPT-4o and execution-verified, with metadata (function name, params, docstring, difficulty) that will make automatic filtering easy — e.g., we can select only the "Instruct/Complete" pytest-style subset and drop the "Online Judge" stdin/stdout subset entirely, then filter further for functions with no imports outside the standard library and no obvious I/O calls. The catch is the CC BY-NC 4.0 license, which blocks any commercial use of a model trained on it — this is the single most important thing to resolve with whoever owns the training-data-rights decision before ingesting 480k rows of it. If commercial use is required, this dataset should be dropped or used only for early experimentation.

**2. AceCode-87K** is the best license/format combination even though it's an order of magnitude smaller. MIT-licensed, 87k questions each carrying ~16 LLM-generated assert-style test cases, already filtered once by the original authors for "noisy" tests. The catch: tests are stored as a bare list of assert strings tied to a question, not as an assembled pytest module, so curation work here is mechanical (wrap the asserts in a `test_x.py` importing from `solution.py`) rather than filtering work — this is exactly the "good raw material, needs assembly" case the task asked us to flag.

**3. nvidia/OpenCodeInstruct** is a volume hedge behind KodCode. It's CC BY 4.0 (no NC restriction, unlike KodCode) and explicitly carries a `unit_tests` field plus a computed pass-rate per row, at a scale in the hundreds of thousands to low millions. It ranks below AceCode/KodCode only because I could not confirm from the card whether the `unit_tests` field is a runnable pytest module, a list of asserts, or an I/O-judge style check — that needs a hands-on sample pull before it can be trusted, but if the format turns out clean this is probably the single best commercially-unencumbered option at scale.

**4. bigcode/self-oss-instruct-sc2-exec-filter-50k** is smaller (50.6k) and messier (function + test are embedded together in one instruction-response text blob that needs parsing), but it has a real quality signal working in its favor: every row was execution-validated as part of StarCoder2-Instruct's self-alignment pipeline, meaning the tests are confirmed to pass against the paired solution already — that's exactly the "test passes against the function" precondition our own filter needs, already done upstream. ODC-BY license is permissive. Curation cost is parsing effort, not correctness-verification effort.

**5. BigCodeBench**, despite being tiny (1,140 unique tasks), earns a place in the top 5 purely on quality: Apache 2.0, `unittest.TestCase`-based (pytest runs these natively), human-curated tasks with an average of 5.6 tests per task. It won't move the 5,000-row target by itself, but it's a good source of hard negative/high-quality seed examples and a sanity-check set, since many of its functions call into real libraries (pandas, numpy, requests-mocked, etc.) — the ones that pass our "pure function, no I/O/network" filter are likely to be unusually well-tested examples worth over-weighting.

## What I'd download first, and why

**AceCode-87K first.** It's MIT-licensed (no downstream legal question), the assert-based test format is the closest structural match to "write a pytest module that imports the function and asserts against it" of anything at meaningful scale, and at 87k rows with ~16 tests each we can likely clear the 5,000-usable-example bar even after aggressive filtering for purity (no I/O), single-function scope, and mutant-killing verification. It is also small enough (1.01 GB) to fully download and process in one pass rather than needing streaming.

**KodCode-V1 second** (pending a license decision) because it is the largest clean, already-pytest-formatted, execution-verified corpus found — if non-commercial use is acceptable for this phase (e.g., research/prototyping before a commercial model is trained), it's the fastest path to comfortably exceeding 5,000 usable pairs with headroom to spare for our own filtering losses.
